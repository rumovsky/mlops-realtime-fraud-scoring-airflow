# Realtime fraud scoring with Airflow

Проект развивает сервис скоринга из ДЗ1. Airflow ведёт размеченную витрину, обучает модель на скользящем временном окне, сравнивает её с действующей моделью и публикует только модель с не ухудшившимся ROC-AUC. Сервис скоринга перечитывает указатель модели без перезапуска.

## Запуск

Нужны Docker и Docker Compose. Скачайте `train.csv` из соревнования Kaggle, указанного в задании, и положите его в `data/train.csv`.

```bash
docker compose up --build
```

Интерфейсы:

- Streamlit: `http://localhost:8501`
- Kafka UI: `http://localhost:8080`
- Airflow: `http://localhost:8081` (`admin` / `admin`)

## DAG-и

`retrain_fraud_model` запускается раз в 5 минут (`catchup=False`) и состоит из задач:

1. `initialize_store` — создаёт размеченную витрину и начальное состояние;
2. `prepare_training_sample` — берёт фиксированное окно из 3 месяцев; ранние 2 месяца идут в train, последний — в test;
3. `train_model` — применяет собственный препроцессинг и обучает CPU-модель CatBoost;
4. `compare_models` — считает ROC-AUC новой и действующей моделей на одном тестовом месяце;
5. `publish_model` — публикует новую модель только при `candidate_roc_auc >= active_roc_auc`.

Для ручной проверки откройте Airflow, включите DAG и нажмите Trigger. При принятии кандидата в `models/current.json` появляется новая версия; при отклонении указатель остаётся прежним. Сообщение Kafka `scoring` содержит `model_version`.

`append_labelled_month` также запускается раз в 5 минут. Он берёт батч из текущего месяца, переносит `transaction_time` в следующий календарный месяц, добавляет его в витрину и удаляет историю старше 12 месяцев. Размер батча — 5000 строк. Идемпотентность обеспечивается таблицей `month_batches` и транзакционным advisory lock: повторный запуск уже добавленного месяца ничего не добавляет.

`data_quality` запускается раз в 5 минут, формирует `reports/latest.html` и завершается ошибкой при нарушении правил. Проверяются:

- наличие и заполненность обязательных полей;
- конечность и неотрицательность `amount` и `population_city`;
- диапазоны географических координат;
- значения `target` только 0 или 1;
- корректность дат;
- уникальность идентификаторов;
- последовательность месяцев окна;
- наличие обоих классов в train и test;
- глубина истории витрины.

В Streamlit доступна ссылка на последний HTML-отчёт Data Quality. Датасет и сгенерированные версии моделей в репозиторий не входят.

## Витрина и публикация

При первом запуске витрина заполняется последними 3 месяцами из `train.csv`, до 5000 строк на месяц в порядке CSV. Следующие месяцы моделируются копированием существующих размеченных транзакций. Это демонстрационные данные для проверки оркестрации; такой тест не является оценкой качества на новых реальных клиентах.

Указатель `training_state.current_month` хранится в PostgreSQL. Пополнение готовит только следующий месяц относительно этого указателя. Переобучение сохраняет снимок окна для конкретного запуска; повтор задачи использует тот же train/test. После сохранения принятого файла модели атомарно заменяется `models/current.json`, затем фиксируется новый месяц в БД. Если процесс завершится между этими действиями, повтор публикации восстановит указатель БД по уже опубликованной версии. При отклонении модели версия и месяц остаются прежними.

Имена файлов моделей определяются ID запуска. Скоринг читает один указатель на файл и версию вместе; препроцессинг одинаков при обучении и применении новой модели. Он использует категориальные поля, логарифмы суммы и населения, признаки времени и расстояние по координатам без кодирования по target. Начальная модель ДЗ1 сохраняется со старым препроцессингом до первой принятой новой версии.

ROC-AUC сравнивается на одних и тех же строках последнего месяца без округления. Равенство допускается; ухудшившаяся модель сохраняется как кандидат, но не становится активной. Значения и решение видны в логах `compare_models` и `airflow/work/<ID>/comparison.json`.

## Проверка

Для первой ручной проверки запустите `append_labelled_month`, затем `retrain_fraud_model` и `data_quality`; дождитесь окончания каждого DAG. Повтор `append_labelled_month` для уже добавленного месяца не увеличивает число строк. Если кандидат отклонён, следующий запуск пополнения готовит следующий месяц, а указатель опубликованного месяца остаётся прежним.

```bash
docker compose exec postgres psql -U fraud -d fraud -c "SELECT * FROM training_state;"
docker compose exec postgres psql -U fraud -d fraud -c "SELECT month, row_count FROM month_batches ORDER BY month;"
```

Загрузите `test.csv` в Streamlit, отправьте строки в Kafka и нажмите «Посмотреть результаты». Версия активной модели видна над формой и в результатах; в Kafka UI откройте `scoring` и проверьте `model_version`.

HTML-отчёты находятся в `reports/` рядом с `models/`; последний можно скачать из Streamlit. Отчёт сохраняется и при нарушении DQ, после чего задача `assert_quality` отмечает DAG как failed. DQ DAG не изменяет витрину и не управляет публикацией модели.

Остановка: `docker compose down`. PostgreSQL хранится в именованном томе; модели, отчёты и снимки задач — в каталогах проекта. Для проверки на чистых данных нужен отдельный клон проекта. Команда `docker compose down -v` удаляет БД, но не очищает каталоги моделей и отчётов.
